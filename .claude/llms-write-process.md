# llms.txt File Serving Process

## Document Purpose
This document explains how GetCited handles llms.txt file generation, why we use dynamic serving, and how to troubleshoot CDN caching issues.

---

## History

### Before v1.9.9.18: Physical File
- llms.txt was written as a physical file to the site root
- Web server (nginx/Apache) served the file directly
- Issue: If user edited content in admin, they had to remember the physical file existed

### v1.9.9.18+: Dynamic Serving (Current)
- Removed physical file, switched to WordPress rewrite rules
- Content stored in database, served via `template_redirect` hook
- Headers set: `Cache-Control: no-cache, no-store, must-revalidate`
- Benefits: Single source of truth, always shows latest saved content

### v1.9.9.25: Added Cache-Busting Verification URLs
- **Problem discovered:** CDNs (Cloudflare, Kinsta) may cache `/llms.txt` responses
- **Solution:** Verification links in admin include timestamp: `/llms.txt?v=timestamp`
- Users can verify their content immediately after saving
- AI crawlers will eventually get fresh content when CDN cache expires

---

## Why Dynamic Serving

### The Problem with Physical Files + CDNs
Physical files don't magically solve CDN caching:
1. CDN caches the response (whether from physical file or dynamic)
2. CDN uses its own TTL policy (can be 1 year for `.txt` files)
3. File metadata changes don't force CDN to invalidate cache
4. CDNs validate with origin only when their cache expires

### Why Dynamic is Better
1. **Single source of truth** - Content in database, no sync issues
2. **No write permission problems** - Works on all hosts
3. **No file conflict management** - One less thing to worry about
4. **Same CDN behavior** - CDNs cache dynamic and static equally

### The Real Fix
The December 2024 issue was caused by a legacy physical file from pre-v1.9.9.18 that got cached by the CDN. The fix is:
1. Delete any legacy physical files (migration handles this)
2. Let dynamic serving take over
3. User purges CDN cache once (one-time)
4. Problem solved permanently

## Current Implementation

### How llms.txt is Served
1. WordPress rewrite rule: `^llms\.txt$` → `index.php?getcited_llms_txt=1`
2. `template_redirect` hook catches the request
3. Content loaded from database (`llms_txt_content` option)
4. Headers set: `Cache-Control: no-cache, no-store, must-revalidate`
5. Content output with `text/plain` content type

### Fallback URL
- `/?llms-txt=1` bypasses rewrite rules entirely
- Useful for debugging if rewrite rules aren't working

### Cache-Busting Verification URLs
- Wizard: `templates/wizard.php` line ~212
- Dashboard: `templates/llms-txt.php` line ~63
- Display: `https://example.com/llms.txt`
- Actual href: `https://example.com/llms.txt?v=1735251234`

## Conflict Detection & Handling

### On Wizard Completion

When user completes the setup wizard, `backup_physical_file()` runs:

1. **No physical file exists** → Nothing to do, dynamic serving takes over
2. **Our legacy file exists** (has `# Generated by GetCited` marker) → Delete it
3. **User's custom file exists** → Move to `llms.txt.bak` (preserved, not destroyed)
4. **SEO plugin's file exists** → Move to `llms.txt.bak`

**Result:** Physical file is removed, GetCited's dynamic serving takes over. User's original content is preserved in `.bak` file.

### How We Detect Other Plugins' Files
1. Check if physical file exists: `physical_file_exists()`
2. Check if it has our marker: `is_our_physical_file()`
3. If our file, delete it (legacy from pre-v1.9.9.18)
4. If not our file, detect SEO plugin source: `detect_seo_plugin_source()`

### Supported SEO Plugin Detection
- Yoast SEO
- RankMath
- All in One SEO
- Squirrly SEO
- SEOPress

### Conflict Resolution (Post-Install)
If a physical file reappears after installation (user re-uploads, SEO plugin recreates):
- Physical file takes precedence (web server serves it before WordPress runs)
- Health check shows warning with specific disable instructions
- `get_seo_plugin_disable_instructions()` provides per-plugin guidance
- User must disable other plugin's llms.txt feature or delete the file

### SEO Plugins with Dynamic llms.txt
If an SEO plugin serves llms.txt dynamically (not physical file):
- Both plugins have competing WordPress rewrite rules
- Whichever hook fires first wins
- Most SEO plugins use physical files, so this is rare

## Troubleshooting

### User reports stale llms.txt content

1. **Test cache bypass:**
   - Try `https://example.com/llms.txt?v=123` (cache-busting)
   - Try `https://example.com/?llms-txt=1` (fallback URL)
   - If these show fresh content, it's a CDN cache issue

2. **Check for physical file conflicts:**
   ```bash
   ls -la /path/to/wordpress/llms.txt
   ```
   If exists, check if it's from another plugin.

3. **Check response headers:**
   ```bash
   curl -I https://example.com/llms.txt
   ```
   Key headers to look for:
   ```
   cf-cache-status: HIT          # Cloudflare serving cached response
   ki-cf-cache-status: HIT       # Kinsta CDN layer cached
   ki-cache-type: CDN            # Kinsta CDN active
   x-kinsta-cache: MISS/HIT      # Kinsta site cache status
   cache-control: public, max-age=31536000  # 1-year TTL (CDN overriding our headers!)
   ```

   **Note:** CDNs override our `Cache-Control: no-cache` headers with their own aggressive TTL (up to 1 year for `.txt` files).

4. **Clear CDN cache:**
   This is a one-time fix - after purging, dynamic serving works correctly.

### User reports 404 on /llms.txt

If `/llms.txt` returns 404 but `/?llms-txt=1` works:
- CDN cached a 404 response from before GetCited was installed
- Same fix: purge CDN cache

## CDN Cache Clearing by Host

### Kinsta (uses Cloudflare Enterprise)

Kinsta has **two separate cache layers** - both may need clearing:

1. **Site Cache** (page cache):
   - MyKinsta → Sites → [site] → Tools → Clear Site Cache

2. **CDN Cache** (edge cache) - **This is usually the culprit:**
   - MyKinsta → Sites → [site] → **CDN tab** → Clear CDN Cache
   - Or: Tools → Clear Edge Cache (if available)

**Important:** Clearing "Site Cache" does NOT clear "CDN Cache". They are separate.

### Standalone Cloudflare

- Dashboard → Caching → Custom Purge → Enter `https://example.com/llms.txt`

### WP Engine

- User Portal → Sites → [site] → Cache → Clear All Caches

### Other Hosts

- Check for CDN or edge caching settings in host dashboard
- Some hosts (SiteGround, Bluehost) have simpler caching that clears together

## Key Takeaways

1. **Dynamic serving is the right approach** - single source of truth, works everywhere
2. **CDN caching is a one-time issue** - purge CDN cache once after installing GetCited
3. **Cache-busting URLs** help users verify their changes immediately
4. **Physical files from other plugins** are backed up (not destroyed) and warned about
5. **Fallback URL** (`/?llms-txt=1`) is useful for debugging - bypasses rewrite rules
6. **Kinsta has two cache layers** - Site Cache and CDN Cache are separate; CDN Cache is usually the culprit
7. **CDNs override our headers** - They set their own aggressive TTL (up to 1 year) regardless of our `no-cache` headers
8. **AI crawlers visit infrequently** - Weekly/monthly visits mean natural CDN expiration usually sufficient
